# DataBasesAndCachePatterns

Ознакомительный проект: сборка конкурентных паттернов Go для работы с БД и кешем
на голых примитивах (`sync.WaitGroup`, `chan`, `context`, `sync.Mutex`, `sync.Once`),
без готовых библиотек — чтобы своими руками увидеть, как внутри устроены
`golang.org/x/sync/errgroup` и `golang.org/x/sync/singleflight`.

Проект не претендует на production-код: тут важна читаемость и сравнение подходов
рядом, а не покрытие тестами и производительность.

## Структура

```
Patterns/
├── err-group-pattern/       # fan-out по шардам: WaitGroup + канал vs ErrGroup
├── moving-later/            # «кто первый ответил» — отмена остальных запросов
└── single-flight-pattern/   # cache-aside и дедупликация одинаковых запросов
```

## Паттерны

### `err-group-pattern` — конкурентный запрос к шардам

Два подхода к одному и тому же: разослать запрос по N шардам и собрать ответы.

- `DistributedQuery` — классика на примитивах: `sync.WaitGroup` для ожидания,
  отдельная горутина закрывает канал после `wg.Wait()`, а сортировки нет.
- `ErrGrop` / `NewErrGroup` / `DistributedQuery2` — самописная реконструкция
  `errgroup.Group`: `context.WithCancelCause` для отмены, `sync.Once` для
  фиксации первой ошибки, `sync.Mutex` вместо канала для записи результатов.
  Первая ошибка отменяет контекст и возвращается из `Wait()`.

Что сравниваем: зачем нужен `close(responseCh)` в отдельной горутине, чем плохо
забыть про ошибку от шарда, зачем `errOnce`, и почему «канал» и «мьютекс» —
взаимозаменяемые способы собрать результаты.

### `moving-later` — гонка до первого ответа

`DistributedQuery` запускает запрос ко всем репликам сразу и возвращает ответ
победителя: буферизованный канал на 1 элемент + `select` с `default`.
Проигравшие горутины просто не могут отправить и выходят.

Что сравниваем: почему канал **буферизованный** (иначе первая же горутина
заблокируется на отправке до приёма), чем это отличается от варианта с
контекстом и `cancel()`.

### `single-flight-pattern` — дедупликация запросов

- `GetUserBalance` — cache-aside без синхронизации: кеш → БД → запись в кеш.
- `GetUserName` — тот же cache-aside, но под `SingleFlight.Do`, чтобы 100
  одновременных запросов одного `userID` не превратились в 100 запросов к БД.
- `SingleFlight.Do` — реконструкция `singleflight.Group`: `map[string]*call` под
  мьютексом, канал `done` для ожидания, `recover` от паники, удаление ключа
  в `defer`.

Что сравниваем: cache-aside против single-flight, зачем нужен указатель
`NewSingleFlight()` вместо значения, почему вызов удаляется из карты (чтобы
следующий запрос не получил устаревший результат), как `select` в `wait`
учитывает отмену контекста.

## Запуск

```bash
go vet ./...
go test ./...
```

Тестов в проекте нет — каждый паттерн запускается вручную или из своего `main`.
